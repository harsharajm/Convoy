## Version lineage

| | what it was | tags |
|---|---|---|
| **v1** | mutual gossip, fanout 1, no participation limit, RPN proposal budget 1000, no per-class metrics | `gossip_seed42`, `gossip_seed7`, … |
| **v2** | pull-only gossip, fanout 2, participation 3, dose gate, frozen-slice snapshots, head-only gate loss, budget 2000, per-class + `AR_S` metrics | `gp3fo2_*`, `gp3fo2fs_*` |
| **v3** | halved anchors, RPN unfrozen, two-group optimizer | `a16rpn_*` (proposed) |

v2 split into two variants on one rule:

- `gp3fo2` — finished clients excluded as gossip sources (reference-faithful).
  Backfired: `clear` holds 7.6x the images of the smallest cell, its last live
  neighbour finished 3h23 before it did, and it spent 84% of its training with
  no eligible neighbour. 231 of 269 slices logged no live neighbours.
- `gp3fo2fs` — finished clients stay eligible as sources
  (`design_choices.pdf` 2.2.1). Currently running, gossip firing every slice.

## Why v3

v2 closed gossip's deficit (0.2398 vs `local_only` 0.2398, was −0.0067) but
the absolute level did not move much, and `joint` — all data pooled, no CL, no
federation — only reaches 0.2568. Every mode sits within 0.017 of that
ceiling, so the limit is the detector, not the algorithm.

The detector is recall-limited, entirely at small sizes:

```
macro mAP     0.2456      <- AP cannot exceed recall
macro mAR@100 0.3481
macro mAR_S   0.2403
macro mAR_L   0.5065
```

Per-class recall tracks small-object fraction almost exactly:

| class | % small | AR@100 | AP |
|---|---|---|---|
| car | 46% | 0.495 | 0.408 |
| person | 44% | 0.390 | 0.287 |
| traffic light | 89% | 0.279 | 0.167 |
| traffic sign | 74% | 0.229 | 0.120 |

Over 1,027,770 training boxes (train split only):

```
p10 12.6   p25 17.4   p50 28.3   p75 54.3   p90 112.1   p99 336.9
```

The **median box (28.3px) is smaller than the smallest anchor (32px)**. 55.6%
of boxes fall below the smallest anchor; 0.09% exceed the largest. The
evaluation's "small" band is area < 1024px² = 32×32 — exactly the smallest
anchor. Every object counted as small was never proposable.

Resolution was tested first and rejected as the fix
(`results/analysis/res_probe.json`): 1.5x upscaling lifts `mAR_S` +0.030 but
drops `mAR_M`/`mAR_L`, netting only +0.011 mAP; 2x is net negative.
Resolution moves every object, anchors move only the floor.

## Changes

### 1. `model.py` — anchors

```
(32,), (64,), (128,), (256,), (512,)   ->   (16,), (32,), (64,), (128,), (256,)
```

A plain halving, justified as "driving scenes contain smaller objects than
COCO". Deliberately *not* fitted to our box percentiles — it lands in the same
place, but nothing is tuned to our data and nothing touches the test split.
(COCO's own `[32…512]` is itself dataset-tuned, so there is no neutral choice
here; only whose data you tune to.)

One size per level, aspect ratios stay `(0.5, 1.0, 2.0)`. `num_anchors` per
location stays 3, so the RPN head's conv shapes are unchanged and pretrained
weights still load.

### 2. `config.py` — unfreeze

`FREEZE_RPN = False`. `FREEZE_BACKBONE` stays `True` — one variable at a time.

### 3. `model.py` — optimizer (the part that is easy to miss)

`build_optimizer` makes a **single** param group at `LR_HEAD = 0.01`.
`LR_PRETRAINED` exists in `config.py` but is never imported — dead code. As it
stands, unfreezing hands pretrained RPN convs the same unwarmed 0.01 as a
randomly initialised head and destroys them in the first few steps.

| group | params | lr |
|---|---|---|
| pretrained | `model.rpn.*` | `LR_PRETRAINED`, ~1e-3 |
| new | `model.roi_heads.*` | `LR_HEAD` = 0.01 |

`reset_momentum` iterates `param_groups`, so it keeps working unchanged.

**Warmup: added.** `LR_WARMUP = 100`, `LR_WARMUP_FACTOR = 0.01`, a linear
ramp per optimiser via `build_warmup`. A deliberate deviation from
`design_choices.pdf` ("none"), recorded here as one.

The reason is *not* the one first written down. An earlier draft said an
unwarmed 0.01 would let the random head destroy the pretrained RPN convs.
That mechanism does not exist: torchvision detaches the proposal path
(`rpn.py:371`, `pred_bbox_deltas.detach()`), so the RPN and roi_heads are
gradient-isolated and the random predictor cannot reach the RPN at all. The
RPN trains only from its own objectness and box-regression losses. What
warmup actually protects against is the *anchor change* - those losses are
computed against anchors the weights never saw, so early gradients are large
and mispointed.

Kept short because the budget is short: the smallest client trained 480 steps
in gp3fo2, so 100 steps is already 21% of its run (2% of joint's ~5280).
torchvision's usual 1000 would be most of a small client's training.

Verified: both groups start at 0.01x, ramp linearly, and land exactly on
1e-3 / 0.01 at step 100 with the 10x ratio held throughout.

### 4. `gossip.py` — payload and gate signal

Neither of these lives in `model.py`, which is why they are easy to miss.

**Payload.** `_head_state` sends every `requires_grad` parameter. Unfreezing
the RPN puts its ~594k weights on the wire: 13.95M -> ~14.55M per exchange
(+4%). More importantly clients start averaging each other's RPNs — a design
decision, not a side effect. Recommend gossiping everything trainable ("what
you train, you share") and renaming `_head_state`, whose name and docstring
both say "head".

**Gate signal: unchanged from v2 after measuring it.** This was first set to
all four loss terms on the argument "gate on what you train".
`gate_noise_probe.py` measured that and it is wrong under the conditions we
can test. Comparing two never-gossiped clients (clear vs rainy, from
`local_only`) on clear's own batch:

| keys | excess | repeat-call noise | signal/noise |
|---|---|---|---|
| head only | +0.0771 | 0.0030 | **25.4** |
| all four | +0.0277 | 0.0059 | 4.7 |

The RPN terms are larger in magnitude and nearly common across clients, so
they dilute the head-loss difference instead of adding to it. Caveat: the
probe loads v2 checkpoints, whose RPNs are byte-identical, so it cannot say
how far v3's RPNs diverge once trained — they train at 10x below the head from
a shared init, so probably little. The deciding argument is isolation: v3
already changes the detector, so leaving the gate exactly as v2 had it moves
one thing, not two. Revisit once a v3 gossip run exists.

### 5. `smoke_test.py`

The check named "backbone/FPN/RPN frozen, head trainable" asserts
`trainable < 50% of total`. At 14.55M/41.3M = 35% it still passes, so it goes
green while testing the wrong thing. Rename and re-scope.

## Do the baselines need rerunning?

**Yes, all four.** This is the difference from the v2 -> `gp3fo2fs` change,
which only touched `sample_neighbors` — gossip-only, so the other three modes
stayed valid. v3 changes `build_model()`, which every mode calls.

| mode | rerun? | why |
|---|---|---|
| `joint` | yes | new detector; also the cheapest test of the hypothesis |
| `local_only` | yes | new detector |
| `sequential` | yes | new detector |
| `gossip` | yes | new detector, plus payload and gate-signal changes |

v2 numbers cannot be mixed with v3 numbers for any mode.

## Order of work

Each step gates the next.

1. Anchors + unfreeze + optimizer groups + smoke test.
   **Gate:** smoke green, loss finite, trainable ~14.55M.
2. **`joint` only**, seed 42, ~3.5h.
   **Gate:** does `mAR_S` move? This is the entire hypothesis. If it does not
   improve, stop — the anchors were not the problem and the remaining ~25h is
   wasted. This step buys the decision for 3.5h instead of 25.
3. `local_only`, seed 42. Re-establishes the non-gossip baseline.
4. Only then `gossip` + `sequential`.

Tag `a16rpn` so v2 results stay intact.

## Bugs found during the v3 build

- **`run_baseline.sh` had `cd ~/OBJ_DET` hardcoded.** Submitting it from
  `OBJ_DET/v3` would have run *v2's* `train.py` against v2's config and
  written v2 results under a v3 tag — a silent wrong answer, not a crash.
  Now resolves to the script's own directory.
- **The smoke test's freeze check tested nothing under v3.** It asserted
  `trainable < 50% of total`; at 14.55M/41.3M = 35% it passed while the RPN's
  state went unchecked. Now asserts the exact split and that `rpn` and
  `roi_heads` each receive gradients and each move on an optimiser step.

## Finding: gossip destroys the signal its own gate needs

`gate_noise_probe.py` was written to test whether the gate is noise-limited.
It is not — signal/noise is 25 on head-only keys. But the numbers say
something else:

- two clients that **never gossiped** (`local_only`) differ by **7.7%** on
  each other's data
- the actual gossip run measured `excess_median` **0.58%** — thirteen times
  smaller

Mixing at lambda 0.5 every slice keeps the clients nearly identical, so by the
time they gate each other there is almost nothing left to detect. That is a
self-defeating loop, and it explains the inert gate across v1 and v2 better
than gate sensitivity does. Raising `GATE_SENSITIVITY` cannot help if the
mixing is erasing the signal. Unrelated to the detector work, but it bears on
whether the gate line of work is worth continuing at all.

## Risks

- **The pretrained RPN may not recover.** 3 epochs per task is short to
  re-adapt a component trained for many epochs at different anchor scales. If
  `joint` gets *worse*, that is the likely cause — try a lower pretrained lr
  or longer warmup before abandoning the idea.
- **Every v2 number becomes incomparable.** All four modes rerun.
- **Two variables at once.** Do not touch gossip before steps 1-3 settle, or
  the detector and the gossip rule move together.
- **Memory.** Backprop through the RPN adds activation memory. The workload
  already needs ~13GB of a 16GB P100 and OOMs if anything else is on the card
  (job 37452 died this way). The preflight guard in `run_baseline.sh` catches
  a dirty GPU. But if RPN gradients push us over on a *clean* card, batch size
  has to drop — which changes the experiment and forces the baselines to be
  rerun again at the new batch size.

## Cost

~3.5h for the step-2 `joint` gate, then ~9h wall clock for the remaining three
if they run in parallel on clean P100 nodes.

## Result (seed 42, all four modes complete)

```
mode         v2      v3      delta
joint      0.2568  0.2854   +0.0286
local_only 0.2398  0.2550   +0.0152
sequential 0.2394  0.2458   +0.0064
gossip     0.2398  0.2406   +0.0008
```

The step-2 gate passed: `mean_mAR_S` moved 0.2403 -> 0.3106, and it moved
*more* than overall recall (`mean_mAR_100` 0.3481 -> 0.4068), so the gain is
attributable to small objects specifically, not a general improvement that
happened to touch them. The anchor hypothesis is confirmed.

But `gossip` barely moved while every other mode gained 2-4x more from the
same detector change. That is not noise - see
`results/analysis/gossip_saturation_finding.md`. Once four of five clients
finish (task 2 finish times span 22:43-23:59), `clear` becomes the sole
active client and the participation rule (`min(GOSSIP_PARTICIPATION,
len(active))`) selects it *every remaining slice, deterministically* - 224 of
its 260 gossip operations happen after it is the last one standing, mixing
toward frozen finished neighbours at ~97% of full lambda dose each time. The
same mechanism, with the same op counts (260/29/24/22/13), is present in v2's
`gp3fo2fs_gossip` and explains its `clear` deficit too. No gossip run across
v1/v2/v3 has been a fair test of the mechanism: the largest client is either
excluded from gossip almost entirely (`gp3fo2`) or unable to stop gossiping
once alone (`gp3fo2fs`, `a16rpn`). Needs a decision before the next gossip
run - see the candidate fixes in that file.

## Carried forward, not part of v3

The gossip gate is still inert: `weight_mean` 0.9825, `excess_median` 0.0058,
zero rounds skipped, `norm_spread_mean` 0.0079. The five cells are
near-identical — total variation ~0.05 on class mix, ~0.02 on box size, and a
cross-client own-vs-other gap of 0.0026 — so there may simply be nothing for a
gate to discriminate. `GATE_SENSITIVITY = 2.0` gives `exp(-2 × 0.006) ≈ 0.99`;
if the gate is meant to act at all it needs to rise one to two orders of
magnitude. Settle this separately from the detector work.
